# 千问实时语音接入实录

本文记录基于阿里云百炼 `qwen3.8-omni-flash-realtime` 开发实时语音对话应用时的两条接入路线与全部已知坑,
供后来者参考,避免重复踩坑。**所有结论均来自真实项目实测,而非文档摘录。**

---

## 一、两条接入路线总览

| | 路线 A:Realtime WebSocket 直连 | 路线 B:AOQ Client SDK |
|---|---|---|
| 适用端 | 任意(桌面/脚本/服务) | Android / iOS / HarmonyOS |
| 接入点 | `wss://{workspace}.cn-beijing.maas.aliyuncs.com/api-ws/v1/realtime?model=...` | 先 HTTP 换 token,再用 SDK 建连(WebRTC 底层) |
| 鉴权 | 连接握手 HTTP Header `Authorization: Bearer sk-...` | `POST https://{workspace}.cn-beijing.maas.aliyuncs.com/api/v1/webrtc/realtime?model=...` 换临时 token(`sid`/`aoqTokenForClient`/`clientRelayEndpoints`/`certFingerprint`/`workspaceIdHash`) |
| 音频 | 客户端自行采集/播放(16k PCM 进 / 24k 出) | SDK 内建采集/播放(Opus 编解码) |
| 回声消除 | **无自带 AEC**,需自行处理(见 2.5) | 底层 WebRTC 自带 AEC(前提是启动顺序正确,见 3.4) |
| 适用场景 | 桌面端、希望完全自控音频链路的场景 | 移动端首选 |

> ⚠️ 两条路线的 **session 配置 JSON 互不通用**——这是本项目最大的坑之一,详见 3.2。

## 二、路线 A(WebSocket)要点与坑

### 2.1 会话初始化
- 服务端先推 `session.created`,客户端回 `session.update` 后收到 `session.updated` 才可推流;
- `qwen3.8-omni-flash-realtime` 必须使用**绑定业务空间**的域名;
- 音频:`input_audio_buffer.append` 发送 16kHz/16bit/单声道 PCM(100ms 一片,base64);输出默认 24kHz PCM;
- server_vad 模式服务端自动切轮(静音判定默认 800ms 可调),客户端不需 commit。

### 2.2 打断(barge-in)
- 收到 `input_audio_buffer.speech_started` 时,若本地正在播放:清空播放队列;
- 需要发送 `response.cancel` 时,**先确认存在活动响应**(否则服务端返回错误事件)。

### 2.3 会话 JSON 结构(WebSocket 路线)
```json
{"type":"session.update","session":{
  "modalities":["text","audio"],
  "instructions":"...",
  "audio":{"input":{"format":{"type":"pcm","sample_rate":16000}},
           "output":{"voice":"Tina","format":{"type":"pcm","sample_rate":24000}}},
  "turn_detection":{"type":"server_vad","threshold":0.5,"silence_duration_ms":800},
  "input_audio_transcription":{"model":"gummy-realtime-v1"}
}}
```

### 2.4 省费用:静音门
持续上传静音也计费(7 tok/s)。本地做"能量门 + 滞回"可把挂机成本归零:
- 低于阈值后**继续上传约 1.5 秒**(保住服务端 VAD 的时间轴,不影响断句)再停发;
- 一有声音 100ms 内恢复;
- 阈值按自己的环境实测校准(本机安静环境实测:底噪 RMS≈25~50、偶发噪声峰值≈450,取 600 可靠)。

### 2.5 回声处理(桌面外放场景)
WebSocket 路线没有 AEC,外放时模型会"听到自己说话"。实测过的三种方案:
- **声纹方案(两版均实测否决)**:白名单(只放行机主)在换麦后相似度掉到 0.4x 临界;
  黑名单(挡 AI 音色)在回放失真后 AI 回声得分仅 0.10、人声 0.01,**无判决间隔**——CAM++ 类声纹对
  外放失真回放的身份特征不敏感,不可靠;
- **物理方案(推荐,EchoGuard)**:检测到播放队列非空时**直接不上传麦克风数据**(播放结束再延迟约 300ms 恢复)。
  效果:回环物理消失、任何人声零影响;代价:AI 说话时无法插话(需按场景取舍);
- **戴耳机**:最简单,回环本身不存在。

### 2.6 计费参考
- 音频输入 7 tok/s、输出 12.5 tok/s;北京地域 输入 6 元/百万 token、输出 12 元/百万 token;
- 文本输入 1.5、输出 4.5 元/百万 token(小头);多轮对话历史逐轮计入输入;
- 单会话最长 120 分钟;关窗断连即停止计费。

## 三、路线 B(AOQ SDK)要点与坑

### 3.1 连接时序(错一步就卡死)
正确顺序:

```
createEngine → startAudioCapture/startAudioPlayer → setAudioEncoderConfig/setAudioDecoderConfig
→ enableSendMediaStream(audio, false) → connect(配置)
→ [回调] 连接成功
→ [事件] session.created → 发送 session.update
→ [事件] session.updated → enableSendMediaStream(audio, true) → 就绪
```

- **坑 1**:等服务端先发 `session.updated` 再发 `session.update` = 双方互等,界面永远停在"连接中";
- **坑 2**:音频设备启动顺序建议 **播放先于采集**——WebRTC 的 AEC 需要播放(render)流先就位做回声参考,
  顺序颠倒可能出现音频管线初始化异常(**"完全无声"**)。

### 3.2 AOQ 的 session.update JSON 与 WebSocket 路线**完全不同**
AOQ 用的是**简化字符串格式,顶层 voice**,而不是 WebSocket 路线的嵌套对象:

```json
{"type":"session.update","session":{
  "modalities":["text","audio"],
  "voice":"Tina",
  "input_audio_format":"pcm16",
  "output_audio_format":"pcm24",
  "instructions":"...",
  "turn_detection":{"type":"server_vad","threshold":0.5,"silence_duration_ms":800}
}}
```

用 WebSocket 的结构发过去,服务端能正常聊天(文本链路通),但**音频链路静默失效**——
表现就是"字幕一切正常,但一点声音都没有"。本项目在这个坑里排查了很久。

### 3.3 音频轨道模式与编解码(无声的头号疑犯)
- `AoqTrackParam.trackMode`:SDK 默认 `Segment`(**不要改成 Stream**)。
  Stream 模式下会命中原生层限制(`subscribe audio sampleRate 24000 is not supported in Stream mode`);
- **Opus 编解码必须在 connect 前显式配置**(编码器/解码器传同一个配置对象):

```java
AoqAudioCodecConfig codec = new AoqAudioCodecConfig();
codec.trackType = AoqTrackType.AoqTrackTypeAudio;
codec.codecType = AoqEncoderType.AoqEncoderTypeAudioOpus;
codec.sampleRate = 16000;   // 关键:实测通过的组合是「轨道 Segment + 解码 16kHz」
                            // (曾把解码器设为 24kHz 以匹配 session 的 pcm24 声明,被 SDK 拒绝:
                            //  "subscribe audio sampleRate 24000 is not supported in Stream mode;
                            //   use Segment mode or change decoder sampleRate";
                            //  SDK 内部会把 24k 输出流转换后交给播放端,应用侧解码器保持 16k 即可)
codec.channel = 1;
engine.setAudioEncoderConfig(codec);
engine.setAudioDecoderConfig(codec);
```

- Opus 插件(`libPluginOpus.so`)需随工程打包;工程缺失时表现为"有数据但解码静音"。

### 3.4 安卓音频规则(应用层必须自己做的三件事)
1. **音频焦点**:播放前 `requestAudioFocus`(USAGE_VOICE_COMMUNICATION),结束释放;部分机型上音频正常但被其他应用压制即此问题;
2. **通话音频模式**:`AudioManager.setMode(MODE_IN_COMMUNICATION)` + 扬声器路由;
   不进入通话模式时,通话类音频流在部分机型上**被系统静默丢弃**(表现同样是"数据全到但无声");
3. **通话音量**:此类音频走 `STREAM_VOICE_CALL`(不是媒体音量!)。建议检测到音量为 0 时自动调起。

### 3.5 诊断经验(排"无声"的正确姿势)
**先埋探针,再改代码**,按层切开:
- 帧观察者(`setAudioFrameObserver` + `onPlaybackAudioFrame`)统计下行帧数与**帧内容非零字节**
  (全零帧=解码问题;有数据=设备输出问题);
- 统计回调(`onStats`)输出订阅字节数/播放音量;
- 设备状态回调(`onAudioDeviceStateChanged` 等)输出播放设备启停与路由变化;
- **别只看"进程活着"**:窗口是否可见、音量值、系统音频模式,都是独立维度。

## 四、通用工程坑

| 坑 | 说明 |
|---|---|
| **tar 生成的 .zip 不是标准 zip** | `tar -a -c -f x.zip` 生成的包,Python `zipfile` 报 `BadZipFile`、PowerShell 报"不支持拆分或跨区的存档",解压残缺→双击闪退。**用 Python `zipfile` 打包**,并做"解压+启动"双验证 |
| **Tkinter 隐藏窗连带隐藏** | `Tk()` + `withdraw()` 后弹出 `Toplevel` 且设置 `transient`,子窗可能**被一起隐藏**(进程活着但用户看不到任何界面)。独立弹窗场景应直接用 `Tk()` 作主窗口 |
| **Kotlin 字符串转义** | 经多层 shell/heredoc 生成 .kt 文件时,`\n` 可能变真实换行导致"字符串跨行"语法错。写源码文件用编辑工具,不要经 shell 转义链 |
| **APK 审计** | 二进制里搜源码级文本不成立:dex 只有方法名/字符串字面量,注释与源码注释不进包;XML 属性会编译成枚举整数(如 `inputType=0x81` 是密码框) |
| **切换预设 = 重连** | 实时会话上下文不可变,换人设/换语言时应主动断开重连(清上下文),避免状态机竞态 |

## 五、音色与多语言

- 音色表见百炼文档「音色列表」,每个音色标注支持语种(如 Tina 支持 36 种语言中的大部分);
- **选音色务必先试听**:同名风格差异很大(本项目实测:某"专业感"音色被听感评价为"急促、不温柔",最终换回柔和音色);
- 多语言场景不必换音色——主流音色(如 Tina)可直接输出日语/俄语;专属音色(如日语名的 Ono Anna)是可选加分项。
